## Claims and locations

- `glance`: 48 tasks, 13 domains — paper abstract and §1. Five-hour wall-clock budget — §4 and repository README. Publication metadata — arXiv version record. These numbers describe the public evaluated release, not the unreleased private set.
- `question`: problem statement/program vs repository/patch — Table 1, §§1–2. Version distinction comes from sources 4–5; no original-version results are ranked against version 2.
- `pipeline`: subtract contribution, retain dependencies/interfaces, restrict editable files — §3 and Fig. 3 caption. Structured LWE exception explicitly retained (§3 footnote 1). Agent/judge isolation, development score and sanitized message, final selection by agent, missing final = 0 — §4, Fig. 4 caption, repository README. Five-hour iteration and task feedback caps follow README.
- `pass`: thresholds — §3 SVG-EAR example: latency ≤0.96 reference; PSNR tolerance 0.25 dB; SSIM 0.01; LPIPS 0.005. All-workload/all-metric condition — §§4–5.1. “Beats” means meeting the task threshold, not strict numerical dominance in every metric.
- `evidence`: 12 reported agents, once per task — §§1, 5.1. Highest reported run pass rate 58%, Claude Opus 5.5/Claude Code; 16 tasks with no passing agent — abstract/§1. Exact printed per-agent results were added in the PDF re-audit below; none are inferred from bar heights.
- SVG-EAR case — §6.3, Fig. 11 caption: GPT-6 Astra faster on every clip and closer to full attention on average, but misses quality on two clips. No unreported point coordinates redrawn.
- BBQ case — §6.2, Fig. 10 caption: register-based counters, faster circuit, largest passing circuit by lookup-table count on largest tested tree; final score ignores size. No unverified speedup displayed.
- QuarterPIR case — §6.1, Fig. 9 caption: two-checksum mechanism, client knows the two groups that may differ, privacy preserved under task constraint, contribution not fully captured by pass or final score. No new cryptographic guarantee claimed.
- `fci`: §5.2 and Appendix D steps 2–5, 9–11, Eqs. (1)–(7), Table 5. Group duplicate outcomes; normalize score margins; share run effect; conditional logistic probability; Kimi K2.7 anchor; ten FCI points = one logit; FDI uses probability of ALL groups integrated over the shared run effect, NOT one metric group's logistic probability.
- Appendix D details retained: reference median over runs, task score spread selection rule delegated explicitly to appendix; scale floor 5.78; failed positive margin censored at ≥0; exact tie omits margin term; 500 task-bootstrap refits with hyperparameters fixed, 90% FCI intervals; FDI intervals computed separately, not attributed to the same bootstrap.
- `limits`: budget truncation counts unfinished runs as missing-final/zero, NOT best-so-far patch — §5.3 and Appendix D step 12. More than 100 private tasks — abstract and §7. Generalisation boundaries and recommended reading unit are explicitly explainer analysis; unscored area limitation is reported in §§6.2, 7.

## Visual and interaction inventory

1. Numeric overview cards (`glance`): original counts and time budget, no implied quantitative bar scale. Checked against sources above.
2. Four-step HTML method diagram (`pipeline`, all four selectable states): teaching schematic. Build → edit/development feedback → choose final → hidden final. Feedback loop expressed in text, not mistaken for model training; hidden reference stays with judge. All state explanations checked in Chinese and English.
3. Two-clip pass-rule lab (`pass`): **invented teaching inputs**, not recorded model outputs or a complete judge. Clip A fixed ratio 0.90 and PSNR difference −0.10 dB; clip B ratio adjustable 0.80–1.10 and PSNR difference −0.50–0 dB. Mean is arithmetic over two clips. Partial check is conjunction of A/B latency ≤0.96 and PSNR ≥−0.25; range restricts differences to nonpositive values. SSIM, LPIPS and other workloads explicitly omitted; four-check success never claims real task PASS. At default B=(0.94,−0.35), mean=(0.92,−0.225), yet B fails quality. At B=(0.96,−0.25) all four checks meet thresholds. At (1.10,0), latency fails. Reset restores default. Readouts use fixed units, no empirical total score.
4. Evidence cards and case-study details (`evidence`): no reconstructed experimental chart, no invented missing model results. 58% retained at reported precision.
5. FCI equation and probability bar (`fci`): teaching evaluation of p=logistic(z); linear bar on 0–100% probability scale, generated from same p as readout. z=−3,0,3 yields about 4.7%,50.0%,95.3%. Conditional on a single group's z; explicitly NOT full task probability, fitted FCI or calibrated forecast. Odds multiplier applies with same run effect.
6. Research formulas and expanded statistical description (`fci details`): explanatory notation maps to Appendix D, no equation-number claim for a modified full likelihood. No fitting executed locally.

## Related-work comparison update — 2026-11-01

Scope: transfer the requested comparison of all 29 efforts into `#related`, with full Chinese/English text. No leaderboard results are merged across benchmarks. Reference numbers [1]–[28] match FrontierCS 2 §2; FrontierCS 2 is the 29th item.

- **AtCoder Heuristic Contests** — [AtCoder Heuristic Contests](https://info.atcoder.jp/overview/contest/heuristic): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. Real heuristic programming contests: submit solvers and improve routing, scheduling or layout objectives. Task-specific objective functions and test instances determine scores and rankings.
- **ALE-Bench [2]** — [ALE-Bench [2]](https://arxiv.org/abs/2506.09050): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. Turns past AHC tasks into standardised algorithm-engineering evaluations, supporting test feedback and visualisation. Contest scores are related to the original human contestants’ ranks, performance and ratings.
- **FrontierCS [1]** — [FrontierCS [1]](https://arxiv.org/abs/2512.15699): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. Expert-designed and reviewed open-ended algorithmic and research problems; submit executable programs. Automatic evaluators assign partial scores and compare against expert references; optima are generally unknown.
- **FrontierCS 2** — [FrontierCS 2](https://arxiv.org/abs/2610.29932): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. Remove a paper’s core implementation; agents edit allowed components and submit patches for development feedback. The final patch must meet all metric thresholds on all hidden workloads against the original authors’ code; continuous scores and FCI are also reported.
- **LiveCodeBench Pro [9]** — [LiveCodeBench Pro [9]](https://arxiv.org/abs/2506.11928): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. Difficult competitive programming problems, with difficulty assessments from Olympiad participants. Correctness tests measure algorithmic reasoning and problem solving.
- **HeuriGym [10]** — [HeuriGym [10]](https://arxiv.org/abs/2506.07972): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. Write heuristic algorithms for combinatorial optimisation, execute them, receive feedback and iterate. QYI captures both valid-solution yield and solution quality.
- **NP-Engine / NP-Bench [11]** — [NP-Engine / NP-Bench [11]](https://arxiv.org/abs/2510.16476): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. Instance generators, rule-based verifiers and heuristic solvers provide a training and evaluation pipeline. NP-Bench checks feasibility and solution quality on NP-hard problems.
- **KernelBench [12]** — [KernelBench [12]](https://arxiv.org/abs/2502.10517): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. Implement faster, correct GPU kernels for PyTorch workloads. Checks numerical correctness and speedup over a baseline; fast_p counts correct kernels exceeding threshold p.
- **Automated LLM Speedrunning [13]** — [Automated LLM Speedrunning [13]](https://arxiv.org/abs/2506.22419): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. Start from an older nanoGPT training script, optionally with hints, and reproduce later record improvements. Measures implementation of known innovations and training speed under quality requirements.
- **Measuring Autonomous AI Research [14]** — [Measuring Autonomous AI Research [14]](https://www.primeintellect.ai/blog/measuring-autonomous-research): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. Prime Intellect’s long-horizon autonomous experimentation study on nanoGPT speedrunning. Tracks speedrun progress under training-quality constraints, multi-day search trajectories, costs and gains.
- **InferenceBench [15]** — [InferenceBench [15]](https://arxiv.org/abs/2607.20468): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. Deploy an LLM inference server and optimise prefill, decoding, concurrent throughput or a combined scenario. Measures speed under hardware, time and correctness constraints against naive PyTorch and other references.
- **SWE-bench [4]** — [SWE-bench [4]](https://arxiv.org/abs/2310.06770): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. A real repository and GitHub issue; diagnose and submit a repair patch. Related failing tests must be fixed while existing functionality is preserved; reports resolved rate.
- **Terminal-Bench [16]** — [Terminal-Bench [16]](https://arxiv.org/abs/2601.11868): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. Complete realistic terminal workflows, including configuration, debugging and data processing. Task-specific tests verify the resulting environment and artifacts.
- **MLE-bench [5]** — [MLE-bench [5]](https://arxiv.org/abs/2410.07095): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. Kaggle ML competitions: prepare data, train models, experiment and submit predictions. Competition metrics and original human leaderboards establish comparisons, including medal thresholds.
- **DeployBench [19]** — [DeployBench [19]](https://arxiv.org/abs/2606.05238): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. Deploy research software from a fresh machine, resolving toolchains, CUDA and dependency compatibility. A hidden pipeline executes the designated experiment and verifies outputs.
- **PaperBench [8]** — [PaperBench [8]](https://arxiv.org/abs/2504.01848): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. Read a paper, build a codebase from scratch and execute experiments to reproduce its contributions. Author-informed hierarchical rubrics: 20 papers and 8,316 individually gradable subtasks.
- **RE-Bench [17]** — [RE-Bench [17]](https://arxiv.org/abs/2411.15114): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. Open-ended ML research-engineering environments supporting search and experimentation. Compares task scores of agents and human experts under matched total time budgets.
- **ResearchGym [6]** — [ResearchGym [6]](https://arxiv.org/abs/2602.15112): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. Keep paper datasets, evaluation tools and baselines, but withhold the proposed method. Propose hypotheses and run experiments; assess task metrics, baseline improvements and research completion.
- **MLS-Bench [7]** — [MLS-Bench [7]](https://arxiv.org/abs/2605.08678): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. 140 ML tasks in 12 domains; improve one targeted system or algorithm component. Reimplement strong baselines in a common framework and calibrate to published performance; control protocols, capacity and evaluation scale.
- **PostTrainBench [18]** — [PostTrainBench [18]](https://arxiv.org/abs/2603.08640): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. Give an agent a base LLM, target task and compute budget; let it choose post-training strategies. Scores downstream performance of the resulting trained model.
- **EdgeBench [20]** — [EdgeBench [20]](https://arxiv.org/abs/2607.05155): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. Multi-domain, very long-horizon tasks with rich, multi-level environment feedback. Studies performance and improvement curves during sustained environment interaction.
- **AIRS-Bench [21]** — [AIRS-Bench [21]](https://arxiv.org/abs/2602.06855): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. Twenty research tasks sourced from ML papers, without baseline code; agents devise their own solutions. Compares experimental task metrics against published results.
- **RSI-Forge [22]** — [RSI-Forge [22]](https://arxiv.org/abs/2610.09426): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. A multi-agent pipeline turns papers into executable environments and independently reimplements methods as references. Automated evaluators compare solution quality; later attempts can inherit previous code and notes.
- **Into the Unknown [23]** — [Into the Unknown [23]](https://arxiv.org/abs/2610.19159): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. A paper and a scientist’s unpublished follow-up direction; produce a follow-up research paper. Scientist-defined necessary conditions and integrity/evidence checks.
- **ReuF2F [24]** — [ReuF2F [24]](https://arxiv.org/abs/2610.27046): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. Open mathematical problems from undergraduate research, and their negations, placed in Lean 4 projects. Machine-checkable formal proofs can resolve the statement or its negation.
- **SWE-smith [25]** — [SWE-smith [25]](https://arxiv.org/abs/2504.21798): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. Synthesise changes to existing Python repositories that break existing tests. Uses tests to construct repair tasks and generate software-engineering training data.
- **FrontierSmith [26]** — [FrontierSmith [26]](https://arxiv.org/abs/2605.14445): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. Change objectives, output constraints or inputs of closed-ended contest problems to create open-ended variants. Build tests and verifiers, selecting tasks that elicit diverse solution ideas.
- **BenchEvolver [27]** — [BenchEvolver [27]](https://arxiv.org/abs/2606.01286): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. Evolve reference solutions first, then derive matching statements and tests. Executable semantics constrain task validity and difficulty.
- **DiscoGen / DiscoBench [28]** — [DiscoGen / DiscoBench [28]](https://arxiv.org/abs/2603.17863): task/input, evaluation/reference and distinction/limits checked against the primary abstract or official description read in this session. Procedurally generate ML algorithm-discovery tasks, such as optimiser or loss-function design. Generated tasks have executable evaluations; DiscoBench is a fixed subset.
