# 论文交互网页制作

将原始研究材料制作成可独立访问、可追溯证据的学习网页。本项目默认交付包括本地制作、目录接入、检查和 GitHub Pages 发布；当次用户指定的语言、深度、风格或交付范围优先。咨询、评审或演练请求按其范围执行。

## 术语问题暂存与批量更新

当用户在阅读过程中连续提出“这个词是什么意思”或要求给词语增加解释时，默认进入术语收集阶段。先把问题、当前解释、页面位置、证据状态和中英文草稿追加到临时记录文件（默认 `/tmp/paper-webpage-term-questions.md`），只更新记录，不立即修改网页。用户明确说“问题结束”“统一更新网页”或同义表达后，再集中审阅待处理条目、确认范围并批量实施；用户明确要求立即更新某一条时，可单独实施该条。

临时记录使用以下字段：术语、用户问题、面向读者的简明解释、论文专属含义、中文/英文文案、页面出现位置、证据来源或“通用定义”、状态（待确认／已核对／已接入）。已完成的术语可保留为历史条目；统一更新后清空待处理条目或将其标为已接入，不把临时记录提交到仓库。

术语浮窗沿用页面已有的双语和可访问性约束：所有可见同词实例复用同一个浮窗，浮窗只放定义和关闭操作；支持鼠标点击、Enter/Space、Esc、点击外部关闭、可见焦点、`aria-expanded`、`aria-controls`、`aria-haspopup="dialog"` 和中英切换。术语解释应区分通用定义、论文中的具体用法和讲解者推断；只有新增论文事实、数值、机制或引用时才更新 `sources.md` 并执行相应证据核验。

## 1. 评估：确定范围并记录基线

先判断任务类型，再选择核查深度：

- **纯样式优化**：只改变排版、配色、间距、响应式布局或不改变科学含义的控件文案。核对受影响的显示与行为，不强制补录整篇证据或重读全部 SI。
- **交互修复**：修复焦点、切换、加载、错误反馈等行为；若改动涉及计算、数值、量尺、状态分支含义或科学输出，同时按科学内容任务核验。
- **科学内容任务**：新建讲解页、新增/修改结论、公式、数据、方法/结构图、科学翻译，或用户明确要求科学审阅，必须核对相应原文、图表及必要 SI，并维护证据记录。仅改变外观不自动触发完整科学审阅；明确的科学审计要求也不能以“样式任务”为由跳过。
- **咨询与审阅**：按请求交付建议或问题清单，不自动扩展到修改、目录接入或发布。

### 定位与基线

- 从当前工作目录用 `git rev-parse --show-toplevel` 找仓库根目录，读取适用的 `AGENTS.md`、仓库说明和目标页面。新页面使用 `papers/<slug>/index.html`；更新页面沿用原 slug、链接及首次发布日期。
- 记录开始时的分支、HEAD、暂存和未暂存差异。已有工作可能来自其他任务；识别本次需要接续的改动，避免覆盖并发编辑，提交时按文件或片段核对边界。
- 先在目录中按标题、DOI、原文链接查重。论文链接确定来源身份；slug 使用简短的小写英文与连字符。
- 读者默认兼顾入门与深入阅读，中文为默认语言并提供完整英文切换。资料和目标已明确时直接推进；只询问会实质改变内容或实现的缺失信息。

- 已有页面改进先运行静态检查，再通过本地 HTTP 检查 1440、768、390px。审计科学表达（按上述范围）、首屏与阅读路径、导航/语言/深度、图表与公式、移动布局、键盘/焦点/ARIA/对比度、异常状态及共享资源兼容性。
- 输出按 P0 必须修复、P1 明显提升、P2 可选优化排序的问题清单；区分已复现、疑似问题和未验证项目，并给出位置或复现条件。先交付评估结果，再修改页面。
- 现有文章只能保留或增加：不得删除、合并替代、下架或移除目录入口；新增文章不能替代旧文。优化不得删减有效内容，可重排或渐进展开。保留原 slug、URL、来源链接、章节 ID、首次发布日期和目录结构。

### 按范围核对资料与证据

- 接受本地 PDF、正式论文链接、DOI 或研究主题。优先读取用户给定版本的正文、图表及必要 SI；联网时使用出版社、正式会议、作者或预印本原始来源。若为研究主题，先确认支撑讲解的核心文献，而非把主题编成一篇论文。
- 对关键结论、公式、数值和实验条件记录出处，能定位到章节、图表、页码或 SI 项目。新建页面或修改科学内容时维护同目录 `sources.md`：记录版本、来源链接、关键主张与证据位置，以及解释范围。纯样式或控件文案修改按改动范围核对，避免扩展成整篇证据补录。
- 区分“论文报告”“作者提出的机制”“教学示意/计算”“讲解者分析”。保留单位、基线、数据集、实验条件及不确定性的含义；重绘图形应能追溯数据，教学滑块不得冒充新实验或经过验证的物理模拟。
- 自绘科学结构逐项对照原文图、正文及 SI，核对维度、拓扑、连接关系和材料／物种间的配位差异；简化绘图仍须保留这些科学关系，标注“教学示意、非晶体坐标”不能补救错误结构。无法可靠重绘时，使用注明出处的原图或裁切图，保留相关结构与必要上下文。
- 核查 AI／ML 方法图、公式和实验图表时，读取 [AI 图示核查要点](references/ai-figures.md)。清点图表时包括 HTML／CSS 流程、隐藏层次、交互输出及结果表，逐项记录核对来源和结论，不能仅统计 `img`／SVG。
- 只有摘要或部分正文时，先尝试根据标题、DOI 或作者提供的链接获取公开原文及 SI；仍不可得时，制作范围限于已核对的内容，明确缺口。可继续设计结构和整理来源；无法支持关键结论时保留本地草稿，列出所需材料，待核对后再发布。
- 原文与 SI 冲突时说明采用的版本和理由。补充研究应独立标注，避免把后续成果归到原论文。

证据记录可参考 [Ln 局部配位的 sources.md](../../../papers/ln-local-coordination/sources.md)，不复制其中仅适用于该论文的限制。

## 2. 设计：将问题映射为可验证的改动

逐项说明目的、影响文件、用户收益及验证方法。优先处理核心结论与图示层次、章节密度、机制—证据—局限关联、图例/单位/来源、交互反馈、双语完整性及手机和键盘体验。只修改与本次任务有关的文件；共享修改须说明跨页影响。

### 内容与交互

采用适合该论文的篇幅和章节，讲解主线通常是：

1. **核心思想**：一句话贡献、关键图示，以及读完应理解的问题。
2. **背景问题**：已有方法、缺口、必要术语和适用场景。
3. **方法机制**：输入、步骤、中间状态与输出，逐层解释公式及假设。
4. **实验证据**：与结论对应的数据、基线、条件、消融和有效范围。
5. **局限与联系**：证据边界、未解决问题、与相关工作的联系和研究启发。

- 用概要、可展开细节或学习深度切换组织层次，避免把全部专业内容堆在首屏；按材料选用，不强制每页具有同一种控件。
- 设计能帮助理解的交互，如算法分步、结构/位点选择、条件或指标对比、明确假设下的教学计算。控件必须改变对应图示或解释，并显示当前状态；按需提供重置。
- 图表注明量、单位、刻度、条件和来源；数据与标签共同切换。测量数据、示意坐标和模型预测使用明确标识。
- 实验数值须逐行逐列对应原表的模型、数据划分、指标及聚合方式；数字正确但列名或“平均分”含义错误同样需要修正。条长、点位和颜色图例由同一份数据与明确量尺生成，避免手调图形夸大差异；教学数值及计算假设在对应图旁说明。
- 参考 [RAG 页面](../../../papers/rag/index.html) 的渐进讲解和 [Ln 局部配位页面](../../../papers/ln-local-coordination/index.html) 的证据关联方式。在下述共享视觉规范内，根据论文设计章节、图形与交互布局，不机械复用同一套卡片。

### 统一视觉与共享页面框架

新建和更新讲解页默认沿用 Research Atlas 首页及现有讲解页的深蓝／青色风格。先读取[共享阅读系统说明](../../../papers/README.md#shared-reading-system)、[共享样式](../../../assets/paper.css)与[共享控制器](../../../assets/paper.js)，以当前实现为准。

- **配色**：背景 `#07111f`、面板 `#101e31`／`#15263b`、正文 `#f4f7fb`、次要文字 `#a8b4c7`、边框 `#293a50`、主强调 `#7de3ff`。优先引用共享 CSS 变量；青绿、淡绿、橙、粉、紫等辅助色用于图表分类、证据类型或提示，并保持含义一致。
- **排版**：统一系统无衬线字体、1180px 正文最大宽度、20px 通用面板圆角及共享标题、章节间距。桌面左右留白 24px，手机 18px；实际字号、断点和间距由共享 CSS 管理。长中英文标题要自然换行，避免单字孤行。
- **导航**：使用共享两行吸顶栏；第一行是返回 Atlas、论文简称、可选阅读深度和语言，第二行是可横向滚动的章节导航，并提供当前章节高亮、阅读进度和跳至正文链接。手机端控件自动换行，章节入口保持可用。锚点偏移使用共享 `scroll-margin-top`，不要叠加全局 `html scroll-padding-top`，以免吸顶语言按钮聚焦时意外滚动。
- **层次与控件**：保留各篇独有的图示、实验模块与深度含义。有三档深度时使用“直觉／机制／研究”（Intuition／Mechanism／Research）；已有“全景”（All）或详情展开按内容保留，不为统一外观强加深度控件。
- **局部图形**：局部 CSS 负责论文专属结构，选择器限定在本页或图示容器内；共享 `.atlas-*` 导航组件由公共资源维护。检查内联样式和 JavaScript 生成的颜色，避免深色页面残留浅底深字或低对比文字。原论文图像保留原色，必要时放在白底图框并配置清晰的图注；保留引用处注入图标的尺寸限制。

## 3. 实施：保持内容与站点兼容

不得为了视觉效果改变事实、实验值、统计含义、公式、尺度或证据边界。发现疑似科学错误时单独记录页面位置、原文依据和建议；未获相应更正授权时不擅自改写。

### 页面实现

- 默认使用原生 HTML、共享本地 CSS／JavaScript、页面内的专属样式与逻辑，以及内联 SVG 或 MathML。现有项目不需要为单页引入框架、构建系统或运行时 CDN。必要的原图等放在页面旁的 `assets/` 并使用相对链接。
- 对 `papers/<slug>/index.html`，在本页样式之后加载 `../../assets/paper.css`，在本页脚本之前加载 `../../assets/paper.js`；`body` 设置 `class="atlas-paper"` 和 `data-paper="<slug>"`。使用其他目录层级时按实际位置调整相对路径。
- 页面状态、内容及渲染函数就绪后调用 `AtlasPaper.init({shortTitle, title: {zh, en}, sections: [{id, zh, en}], depth, legacyHeader, allowBoth, onLanguageChange})`。`sections` 对应真实章节 ID；`depth` 是可选的现有深度控件 DOM，`legacyHeader` 是迁移时要移除的旧顶栏 DOM，无则传 `null`；`allowBoth` 默认设为 `false`，完整实现中英对照的页面可设为 `true`。
- 控制器会移动深度控件并生成公共顶栏、导航和进度；`onLanguageChange(lang)` 在初始化时同步调用，随后每次切换都会调用，因此回调所需状态须提前初始化，不能依赖本次初始化尚未返回的控制器变量。返回对象提供 `lang`、`setLanguage(lang)` 和 `refresh()`。迁移旧页时清理依赖旧导航、语言按钮或进度元素的事件，避免重复控件与已移除节点引用；共享语言按钮使用 `data-atlas-lang`，避免与本页的 `data-lang` 事件混用。
- 页面支持静态托管；核心内容和交互尽量不依赖网络。使用本地资源时避免从 `file://` 读取需要跨源请求的数据；通过本地 HTTP 服务检查与部署环境一致的行为。
- 图片阅读器须显示加载与失败状态，保证最终图片、图号、图注和选中按钮对应同一选择；新图未就绪时避免旧图冒充当前所选图。连续切图时忽略过期加载结果，防止旧请求覆盖新选择；预加载可用于改善体验，但不能替代状态处理。
- 设置 UTF-8、`title`、`html lang`、viewport、章节锚点、论文来源及返回站点链接。主内容使用语义化结构，SVG 规则限定作用范围，避免污染公式、图标或引用插件注入的元素。
- 中英切换覆盖正文、导航、图内文字、工具提示、交互反馈、页面标题和无障碍标签；中文模式中的说明性英文标签也应本地化。模型／数据集名、公式符号、原论文标题和正式引用可保留原文。双语检索等教学例子需要保留中文源句时，标记 `data-language-example="zh"`、`lang="zh-CN"`，并提供英文释义。
- 语言初始化、URL、存储和跨页链接交给共享控制器：有效 `?lang=` 优先于 `atlas-lang`，再回退中文；仅保存 `zh`／`en`，`both` 可在支持对照的页面 URL 中使用。存储不可用时仍可切换，更新语言时保留其他参数和锚点。
- 静态内容使用明确的翻译键、稳定的精确文本绑定或成对双语模板；动态说明根据当前实验状态输出。避免可逆的全页字符串替换或模糊子串替换。SVG 文字、`alt`、`title`、`aria-label` 等按当前语言单独更新。
- 语言和深度切换保留滑块值、步骤／图表／节点选择、测验结果、展开项、滚动位置与键盘焦点。优先更新文字和输出容器，避免为语言切换重建整个正文或输入控件。默认中文、显式英文链接和刷新后的语言选择均需可用。
- 窄屏下重排布局；宽表格和公式可在容器内滚动。使用真实按钮、可见焦点、输入标签、可读对比度，并尊重减少动态效果的系统偏好。

### 按任务需要接入站点

先读取 [论文目录指南](../../../references/paper-catalog-guide.md)，以其中的当前结构为准。

- 为论文目录中的真实条目设置 `p: "./papers/<slug>/"`，补齐双语简介和必要的标签翻译。相同 `u` 标识同一论文；任一主题设置讲解链接即可共享，显式设置的链接应保持一致。
- 新论文尚未收录时，依据原文元数据和现有主题结构加入条目；仅在需要时同步对应研究路线。不要为纯研究概念页伪造作者、会议或单篇论文记录；这类页面从相关 README 或合适的主页知识入口接入。
- 为首次发布的论文页在顶层 `explainers` 写入 UTC 日期 `YYYY-MM-DD`；修改已有页面保留已有日期。若此前仅保存草稿，则在实际发布时确定日期。
- 首次创建时间单独存入顶层 `explainerCreatedAt`，使用 UTC ISO 精确时间，生成后保持不变。首页“近一周的讲解页”按首次创建时间筛选最近七个 UTC 日、按创建时间倒序，同日也区分先后；更新旧页不重新进入列表或置顶。已有脚本仅在缺少创建时间时从页面文件的 Git 首次新增提交初始化；其 UTC 日与首次发布日期不同或无历史时，回退首次发布日期的 UTC 午夜。最近更新时间仍保存在 `explainerUpdates` 以兼容发布流程，但不用于首页近期排序；不能通过改写首次日期或创建时间置顶。
- 更新页面自己的 README，以及仓库和论文集合 README 中相关的入口或说明。保留已有站点搜索可见性设置。

## 4. 验证：覆盖变更与关联行为

按设计中的验证方法检查最终版本，修复后重跑受影响检查。审阅只报告结果；修改任务必须实际验证。静态检查、浏览器行为和科学证据分别记录，任何一类通过都不能代替其他类别。

### 静态检查

从仓库根目录运行检查器（将示例 slug 替换为本次页面）：

```bash
paper_web_root="$(git rev-parse --show-toplevel)"
python3 "$paper_web_root/.agents/skills/paper-webpage/scripts/check_page.py" \
  --root "$paper_web_root" --slug your-paper-slug
```

- 检查器只读，使用 Python 3 标准库和 PATH 中的 Node.js；退出码 `0` 表示检查通过，`1` 表示检查问题，`2` 表示命令参数错误。修复错误后重跑。
- 检查页面元数据、字面量重复 ID、本地资源存在性、内联 JavaScript 语法和本页目录接入。它不执行 JavaScript，不请求远端资源，也不证明科学内容正确。动态 DOM、页面内锚点、双语完整性和交互仍需浏览器核对。
- 纯概念页或目录接入前可加 `--page-only`，该模式明确跳过论文目录检查；发布概念页前仍需验证其实际站点入口。论文页发布前必须通过默认完整检查。

### 浏览器与科学验证

按需读取 [浏览器验证操作参考](references/validation.md)，复用现有 Playwright 环境、全站回归和阅读专项检查。最低覆盖：

- 1440、768、390px 首屏及全部章节，图表、长标题、全部深度和展开内容；保存并查看截图。
- 中英文、支持的对照模式、刷新、直接英文 URL、语言/深度切换后的输入、选择、展开、焦点和滚动状态。
- 键盘 Tab/Enter/Space、焦点、可访问名称与对比度；图片慢加载、失败/重试、快速切换、适用的空状态；控制台、资源、锚点、链接和横向溢出。
- 修改共享资源时运行全部页面静态检查、共享 JS 语法检查及全站回归；单页改动按影响范围验证。
- 科学内容任务按证据清单核对实际显示的两种语言及相关状态，尤其是方法箭头、公式分支、数值行列、单位与量尺；纯样式任务确认这些语义未被改动。

交付修改摘要、文件列表、对应用户收益、科学内容/引用变更情况、已运行检查和结果、未验证项、本地预览或页面路径，以及发布剩余事项。核对原有文章和入口全部保留；记录新增文章。关键内容或交互尚未确认时保留本地成果。

## 提交与发布

按当次用户指定的交付终点执行；本地交付、草稿或纯审阅不触发发布。需要发布时使用以下流程，保留既有部署方式。

1. 读取远端和 GitHub Pages 配置，确认发布目标。本仓库当前为 `origin/main`、根目录和 GitHub Pages；实际配置有变化时以查询结果为准，不擅自改部署方式。
2. 获取最新远端状态。发布工作基于最新发布分支整合；当前工作区存在无关差异或未发布提交时，使用干净的隔离工作区移植本次文件/片段。核对待提交差异和将被发布的提交，完整检查最终待发布版本。在最终发布工作区确认当前目录指南及 `scripts/update-explainer-updates.cjs`；当前检出缺少该脚本时，先核对并整合已有实现，避免另造一套时间元数据流程。
3. 用明确文件或片段暂存本次页面内容、资源及目录入口，写入具体提交说明。避免把其他任务的未提交改动或无关提交带入发布。
4. 内容提交完成后，从最终发布工作区根目录运行 `node scripts/update-explainer-updates.cjs`；脚本依赖页面目录及本地资源的 Git 提交时间，未提交编辑不会计入。核对生成目录、首次发布日期与已有创建时间未变和首页近期排序，提交生成的目录后再普通推送两次提交。远端前进导致拒绝时，获取更新并整合、复查；若内容提交时间改变则重新生成时间元数据，保留已有创建时间。遇到需要判断的冲突时保留本地成果并报告。
5. 每隔约 30 秒查询 Pages 构建，最多等待 10 分钟；确认成功构建包含本次推送的最终提交，避免把之前的成功状态当成本次发布完成。失败时读取构建错误；修正明确且属于本次任务的问题后重跑必要检查。
6. 检查线上讲解 URL、对应目录入口及资源，核对标题和一处能识别本次更新的内容，而不只检查 HTTP 状态；同时依据首次创建时间核对本篇是否应在首页近期列表及其位置，同日创建也应按先后排序，更新旧页不得重新入列或置顶。若已推送但构建失败、超时或线上内容未更新，准确区分这些状态并交付可继续处理的提交与链接。

发布后在上述交付信息中补充线上链接与实际发布状态；未发布时明确剩余事项。
