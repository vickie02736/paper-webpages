# 提交与发布

交付终点见 SKILL.md“交付终点与授权”。需要发布时使用以下流程，保留既有部署方式。

1. 读取远端和 GitHub Pages 配置，确认发布目标（`gh api repos/<owner>/<repo>/pages`）。本仓库当前为 `origin/main`、根目录和 GitHub Pages 传统构建；实际配置有变化时以查询结果为准，不擅自改部署方式。用户要求经 PR 交付时，推送功能分支并开 PR，不直接推送 `main`。
2. 获取最新远端状态。发布工作基于最新发布分支整合；当前工作区存在无关差异或未发布提交时，使用干净的隔离工作区移植本次文件/片段。核对待提交差异和将被发布的提交，完整检查最终待发布版本。在最终发布工作区确认当前目录指南及 `scripts/update-explainer-updates.cjs`；当前检出缺少该脚本时，先核对并整合已有实现，避免另造一套时间元数据流程。
3. 用明确文件或片段暂存本次页面内容、资源及目录入口，写入具体提交说明。避免把其他任务的未提交改动或无关提交带入发布。生成页连同其编辑源和生成器一起提交（见 [site-integration.md](site-integration.md#生成页与编辑源)）。
4. 内容提交完成后，从最终发布工作区根目录运行 `node scripts/update-explainer-updates.cjs`；脚本依赖页面目录及本地资源的 Git 提交时间，未提交编辑不会计入。核对生成目录、首次发布日期与已有创建时间未变和首页近期排序，提交生成的目录后再普通推送两次提交。远端前进导致拒绝时，获取更新并整合、复查；若内容提交时间改变则重新生成时间元数据，保留已有创建时间。遇到需要判断的冲突时保留本地成果并报告。
5. 每隔约 30 秒查询 Pages 构建，最多等待 10 分钟；确认成功构建包含本次推送的最终提交，避免把之前的成功状态当成本次发布完成。失败时读取构建错误；修正明确且属于本次任务的问题后重跑必要检查。
6. 检查线上讲解 URL、对应目录入口及资源，核对标题和一处能识别本次更新的内容，而不只检查 HTTP 状态；同时依据首次创建时间核对本篇是否应在首页近期列表及其位置，同日创建也应按先后排序，更新旧页不得重新入列或置顶。若已推送但构建失败、超时或线上内容未更新，准确区分这些状态并交付可继续处理的提交与链接。

发布后在交付摘要中补充线上链接与实际发布状态；未发布时明确剩余事项。
